「为什么不换个做法」的答案都在这里：每个条目记一件已经定型的架构取舍——选了哪个做法、否决了哪个、代价落在哪里、改它要连带碰谁；动手改结构、评审方案或打算推翻某个做法之前先读一遍。

## 天光与海面

### 水下仰视的介质选择
相机浸在海水里、往上看水面，一次解决三件事：水的吸收让深度直接等于亮度，曝光因此有了物理载体；水对红光的吸收比蓝绿快一个量级，一天的变化落在色温而不是亮度上；水面波纹把阳光折射聚焦成焦散投在沙底，画面因此有了一块被光照亮的「地平」。换成空气里的天光，亮度几乎只由太阳高度决定，浅色主题在夜里要够亮就只能硬拉曝光，很假。

### 以 FFT 波场取代解析波叠加
十来个手写正弦项的和有两个治不好的病：方向固定的平面波互相干涉，出来是一层平行条纹；焦散另用一个噪声场单独造，与波场没有导数关系，光网的形状跟水面形状对不上。换成 FFT 之后波高、斜率、拉普拉斯是同一个场的精确导数，热点路径也从每像素一堆三角函数求和变成一次纹理取样，成本与屏幕分辨率无关。场与网格的单源约束见 adr/0002。

### 取自 clearwater 的谱形与本机位尺度
主峰、涌浪、尾巴三个 lognormal 项叠在 k⁻⁴ 上，方向性用 |k̂·ŵ|² 加一点顺风/逆风不对称，比单峰的 Phillips 更接近真实海面；绝对幅度没有物理意义，外观由斜率均方根决定，所以谱的方差在 CPU 侧算准后整体缩放到目标斜率。主峰波长比参考项目大一档是刻意的——参考项目站在岸上看几米外的浅水，这里是水下透过窗抬头看，同样的主峰在窗里会变成一层细密的霜。

### 日月面按点扩散函数展开
水面法线的抖动宽度本身就是点扩散函数：角宽度若远小于抖动，就只有恰好把视线掰到日面上的像素才亮，画面上是一把从太阳位置放射出去的细针，读起来像云母、拉丝冰或彗尾。宽度是物理量，峰值是艺术选择——按通量守恒压下去太阳就彻底没了，所以日面写成色相、宽晕、焦散撕碎三层。窗内那层光网必须封顶：焦散上限可以很高，原样乘进窗心会把起伏压成一块白平台，色相也一起漂掉。

### 直射光柱整条链的删除
焦散是二维图案，沿光路投影回水面得到的是斑块不是柱子；想把斑块拉成柱得让胞元远大于积分长度，结果只是把斑块加粗，同时把正文带的明暗幅度拉大、逼着薄膜加重。参考项目那种硬光柱靠折射网格加屏幕空间面积，而它的相机在水面之上俯视浅池，与这里的水下仰视是两回事。粗带焦散、色散取样与星点倒影一并删掉，旧版那个「光柱与底光强度比」的旋钮不再有消费者；这几项原本都写守均值形式，去掉前后平均亮度不变，曝光与薄膜的校准不用重测。

### 夜里的主光源接力
太阳落到地平线以下时直射光不是「变小」而是「没有了」，接上的是月亮；两样都没有的夜里只剩气辉与城市辉光，它们没有方位，水下的光柱于是收成一束很弱、很正的底光——这条链子决定夜里的画面不会死。满月的照度比太阳弱好几个数量级，照物理比例给会把夜里直接沉成黑，所以月亮按美术可用的强度给，亮度再交给闭环收回来。

### 会聚算子与实测反算的焦散陡度
折射把光偏折，偏折的空间导数就是局部面积伸缩比：面积压到 1/|J|，辐照度就乘 |J|，高度场近似下焦散可以从拉普拉斯直接出来；1/|J| 在过零处发散，真实水里那正是焦散线最亮的地方，夹住下限是在替像素积分做近似。λ 决定亮点有多稀疏，而 σ_lap 是谱的产物、换风速就变，所以 λ 由 CPU 按实测反算传进来，亮暗比才不会随风速漂。

### 三次 B 样条取样与倍频旋转场
硬件双线性给出的斜率是分片线性的，高光沿纹素格子折出硬脊，在整片天被折射掰来掰去的窗里尤其明显；B 样条核 C¹ 连续，用四次双线性取样近似，换回纯双线性的确定性对照里差异正落在窗的高光脊上。倍频场取旋转角、缩到小于一倍：斜率按链式法则合并，焦散是 1/|J| 这类非线性场、不能线性相加，改用两个均值为 1 的独立场相乘再夹回上限。

### 解析波包的交互涟漪
点击产生的是一圈向外跑的环形波，包络乘正弦有闭式解，斜率与拉普拉斯对 r 求导即得，一次 hypot 一个环、最多几个环，比再开一条 FFT 链便宜得多。代价是不反射、不干涉——环与环线性相加，而那正是线性波近似；包络尺度按这台相机的机位定，参考项目里半米量级的环在这个距离上只剩十来个像素。

### 角频率的公共步长量化
ω 向下取整到公共步长的整数倍之后，整个海面在一个固定周期后精确回到起始相位，新标签页开着一整天也看不到跳变；代价是最慢那几支波的相速最多差几个百分点，肉眼看不出来。上一版不做这个量化时，周期不同的波过一段时间就错开，出现一次硬跳。

### 竖直视场角作为构图前提
画面被地平线切成地板与光窗两块，各自占比只由俯仰角和视场角决定：视场角一窄，光窗和地板就在抢同一块画布，怎么调俯仰都拿不到「亮天窗 / 暗水体 / 亮沙地」三段同时在场的剖面。超广角本身也是水下摄影的本来面目。

### 背景而非演示的相机与时钟
相机几乎不动（指针只带一点点视差），波纹漂得很慢，目标帧率刻意低——天空的变化本来就极慢。水面时钟是把时间轴整体乘一个倍率，不是另造一套慢动作：波与波之间的相对关系（色散、聚焦、焦散）完全不变，所以看上去仍然是「真的水」；按真实速度走又太快，眼睛会一直被波抓过去。点击涟漪同理挂在 window 上而不是画布上（背景层是 pointer-events: none，收不到事件），但事件目标是可交互元素时要跳过——点按钮已经有一整套反馈，再在同一个位置开一朵水花是抢戏。

### 带滞回的区间式自动曝光
可读性是一个不等式而不是等式：低于下限才抬、高于上端才压、带内一律不动，可读性本身完全交给薄膜。但控制器必须有回程：统计量本来就会随焦散网漂过而起伏，没有回程的控制器是一台棘轮，某一帧恰好落在下限以下就永久抬了一档，几轮之后整幅被推进 ACES 肩部、纵向层次全平。设定值只能取整幅中位数，不能取正文带的分位数——带子整体落在窗里，而窗里那层碎丝是故意画出来的，拿它当设定值等于要求「连碎丝都得亮」；用 min 更是陷阱，画面里只要有一个角落是黑的，增益就会顶到上限、薄膜拉满。

### 只为后处理引入的 three.js
水是几百行自写的 GLSL，three.js 的 Water2 与 Reflector 都默认相机在水面之上，水下仰视根本没有实现，换不掉；真正买到的是 EffectComposer 与泛光——焦散的高光必须溢出到邻近像素才有「亮」的感觉，单 pass 做不到。附带拿到尺寸管理、上下文丢失处理与程序缓存，代价是 three 成了唯一的运行时依赖，见 adr/0003。

### 低分辨率渲染与浏览器放大
水的散射是低频信号，低分辨率渲染再让浏览器放大，肉眼分不出来，而探针的读回量与分辨率同阶。画布的像素尺寸刻意就是渲染分辨率，不要改成「画布满分辨率 + 合成器低分辨率」——那样每次探测都要回读整块画布、把 GPU 管线掐停一段可观的时间。

## 首帧与主题

### 首帧让位给页面的四步延后
渲染器只能 import type：静态 import 会把它连同 three.js、后处理与一串 ?raw 着色器一起拖进挂载之前的依赖图，时钟、搜索框、磁贴的首帧全在等它，真正的加载发生在 boot 里的动态 import。createSkyRenderer 是同步的，里面挤着编译链接、波场标定的阻塞回读与波谱生成，所以调用要挪到 rAF → setTimeout 之后——直接写在 rAF 里等于没延后，回调仍然跑在本帧绘制之前。建好之后先空跑一趟完整管线、再晚一帧通知可以露脸：各 pass 要到首帧 composer.render 时才逐个编译，紧接的那次 readPixels 也是同步阻塞，这两段都该花在画面还全透明的时候。

### 两态主题的边界
首次打开按系统偏好决定，用户手动切换之后就不再跟随系统——两态模型里没有「跟随系统」这个选项。主题变化还要同步 color-scheme，否则深色下滚动条与原生表单控件仍是浅色。

### 按量的性质分类的过渡插值
只有真的在两端不同的量才参与插值（差在哪见 adr/0004）。辐射量与乘性强度走逐通道几何平均，离散量一律取目标帧；线性插一条逐通道指数曲线，中段会系统性偏高偏灰绿，浅→深和深→浅都会经过一段「不是两片水里任何一片」的颜色。沙面不能线性走到 0，也不能取有沙那一侧——把「没有底」当成一个很远的底、让距离连续走过去，两头都不需要额外的淡出参数。

### 元素级测量、整幅渲染的薄膜
薄膜只留一层整幅、大羽化的径向渐变，但驱动量取所有元素里最亏的那一个：探针逐框量，浅色按每个元素自己的文字颜色反算需求。逐元素补丁在对比度数字上确实有效，画面上却是十几条深浅不一的横带，而薄膜的第一要求是「像雾」而不是「像贴片」。代价是径向渐变的平台必须盖住全部正文，驱动量按满强度算才成立——元素落在衰减段上时，同样的 alpha 补不到它头上。

### 语义 token 作为颜色的唯一真源
背景跟着时段与主题变，同一个颜色值会落在完全不同的底色上，所以界面只取「正文 / 次级 / 弱化」这类语义 token，而不是固定的色阶值；圆角只留四档、层级集中声明，组件里不写裸色值与裸 z-index。改色该改 token，而不是逐组件打补丁。

## 磁贴与站点

### 磁贴入场的竖直沉落与配角定位
上一版向参考站的横向扫掠看齐，但那个前提在这里不成立：PC 全屏时十来个磁贴排成一行，行项恒为零，剩下的行内错开比单格动作还短，读到的只是「整条带子从左往右洗了一遍」。更关键的是层级与代价——这一页的主角是时钟与搜索框，磁贴带在视野下缘，横向位移量级压过 hero，配角比主角还响；而玻璃面带 backdrop-filter，多个玻璃面同时横移，合成器每帧都要按新位置重采样背后的 WebGL 天空。代价是 PC 全屏单行时不会「像一道波」，这是选定的方向。

### 锚定 hero 节拍的起波
起波原先接在数据就绪上，时刻就由 storage 的往返决定，同一份构建连续打开会落在首帧之后一个很宽的区间里，正好压在问候与搜索框那两拍上，每次都不同。时间轴改成由人决定：锚点取 hero 的第几拍，真实起波取「数据就绪」与「锚点」的较大者。代价是要一块遮到真列表就位的幕布（否则先闪种子站）、一个只防 storage 永不返回的兜底定时器，以及把节拍抽成共享常量——以后新增的入场层不能再自己计时。

### 浮起卡片的磁贴克隆
另画一张卡片要重新决定图标是「真图还是首字母」、站点色、圆角与阴影，几处各算一遍就有错配的风险；克隆磁贴本体则让浮起的卡片和它下面那块长得一模一样。克隆体是纯视觉副本：摘掉 tabindex、aria-hidden 与验证钩子，去掉站名与操作按钮，只留「拿在手里的图标」。

### 首字母配色的约束与撞色探测
浅色的首字母配色要同时满足三件事：明度锁进同一窄区间才配得上白字的 WCAG AA、饱和度比常见 UI 色阶低一档才不至于把整页拖成水彩、颜色数量足够多才不至于同屏出现两个同色（早期色少时「知乎」与「哔哩哔哩」撞成同一个粉色）。深色不能复用浅色色板，同一色系要换高明度版本并配深色文字；撞色时按列表顺序线性探测下一个空位，代价是只有发生过撞色的磁贴在增删或排序后才会变色——一屏两个同色看起来更像 bug。

### 跨宿主复用的同一套组件
设置页直接复用新标签页的搜索框与磁贴网格，弹窗与侧边栏只保留最少入口，不另写一套管理 UI——否则同一套增删改、排序与主题逻辑要在三处维护。三者写同一批 storage ref，新标签页通过 storage 的 onChanged 自动同步，所以设置页不需要「保存」按钮；辅助界面里的磁贴与搜索预览一律开新标签页，同标签页跳转会把宿主自己顶掉。

## 存储与迁移

### 图标缓存的 localStorage 选型
磁贴必须在首帧拿到图标，异步 storage 会晚一帧、先闪首字母再跳成图标；localStorage 同步、在扩展的各个页面间共享、跨浏览器重启仍在。图标接口是页面级资源，模块级 Map 随页面销毁，所以缓存必须落到持久层，并且存图标字节本身而不是「有没有图标」的布尔值——只存布尔值并不能省掉取图请求。

### 否定结论的短保鲜期
「这个站点没有图标」是对 Chrome 图标库当下状态的猜测，而那个状态会变：用户后来访问了站点、Chrome 抓到图标、或刚装扩展时图标库还冷。保鲜期要短到足够覆盖连着开一批新标签页的窗口，又不会把过时判断压太久；真图标过期时不要当没命中——先用旧图立刻显示、再在后台重验，退回首字母只会白白闪一下。

### 备份的纯数据层与碰环境层
格式、校验与序列化放在不碰 Vue / DOM / storage 的纯函数层，文件读写、下载与落盘放在 composable；纯函数层刻意不 import storage，因为那个模块被引入时就会去读扩展 storage。这样解析可以单独喂字符串验证，失败原因也能结构化返回给界面，而不是逼调用方解析异常消息。

### 自建的备份格式
导入别人的结构要递归猜站点藏在哪个文件夹或分组里，猜错会静默丢站点；借来的格式也没有问候语、默认引擎与主题的位置，导入一次等于丢设置。代价是用户不能直接迁移别家新标签页的站点，只能重建或手工转换，而自有格式一旦发布就要长期维护版本分支。导入结果必须把被跳过的站点与设置项显示出来——静默丢弃正是自建格式要避免的事。

## 构建与验证工具

### 构建配置导入模块的零依赖约束
theme-boot 守卫与 UnoCSS 的 safelist 会在 Node 侧直接 import themeBoot 与 searchEngines，所以 themeBoot 必须保持零 import、searchEngines 不能引入运行时依赖，否则配置加载会被牵连，把浏览器或 Vue 的运行时拖进构建进程。新增依赖前先确认它不会被这两个模块带进去。

### 终态截图与时间线采样的分离
「改完长什么样」只要终态整屏，前提是字体已落地、入场动画已经走完，否则拍到的是回退字形与中间态，评审结论就错了；「动画过程发生了什么」必须靠定格或逐帧采样，而采样中途绝不能截图，因为截图会强制布局与合成、把逐帧读数打出空洞。两类脚本因此分开、不合并：需要「第几毫秒长什么样」时一律走浏览器的录屏协议，帧自带浏览器给出的时间戳，截图只用于终态与人工复核。代价是产物为压缩帧、帧率受编码器与背压影响，还要额外做时间戳与墙钟的对齐。

### 天光问题的分层拆解与逐行对数
视觉出问题最怕「看着不对但说不清哪层不对」，所以把画面拆成最终态、关掉薄膜的纯天空、关掉 WebGL 的 CSS 兜底三张分别拍，一次回答「问题在着色器还是在薄膜」以及「降级路径本身好不好看」。着色器常数在一份重写了同一套数学的台架上搜出来，台架给预测、真机逐行给像素，哪一行对不上就把问题锁死在哪一行；拿旧目标或旧基线去比，只会得到一片无法归因的偏差。

### 否定结论的反向对照
要证明「扩展没有往网页里注入任何东西」，先手动造一个真注入再让检测器抓它——否则「没找到」可能只是检测器写错了。目标页用本机 HTTP 提供以命中全站匹配规则，不依赖外网。

### 会误报的断言的危害
落定残留这类断言只在「没有入场动画在跑」时才成立，前置条件不满足要记跳过，而不是记通过或失败；断言还要自检有没有真的验到东西——收集窗口收到零条动画、逐帧全已落定、动画分组表为空，都必须硬失败，而不是静默落一份看起来通过的产物。
